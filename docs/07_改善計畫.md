# 改善計畫

本文件追蹤專案的改善項目。新增、調整項目時，同步更新「狀態總覽」與對應項目的現況、做法及驗收標準；新發現的問題也記錄在此。

項目完成後，在狀態總覽的「結果」欄寫一句做法與驗收結果，並附上 commit hash，然後刪除下方該項目的細節段落。完整改動可由 commit 查詢。

狀態：`待辦`、`進行中`、`待確認`（需先決定方向）、`完成`、`不處理`

編號前綴：D 文件與設定、F 功能、B 程式錯誤、P 效能、T 測試。

**評測範圍（2026-11-23 決定）**：專案著重車廠手冊，Samsung、EPSON 等非車用手冊不再重跑評測。原本以 Samsung 題組驗收的項目改用 SM3E 題組（Q1 `72652503`、Q2 `8461ea5f`、v4 `ce52772d`、03_* 系列）驗收；只能用 Samsung 驗收的項目改為「不處理」，程式保留。

## 文件與設定問題

### D-09 範例題目集答案為佔位文字

- **現況**：`docs/06_題目集範例.json` 兩題的 `expected_answer` 都是同一句「先確認設備已關閉，準備指定工具，並依序完成安全檢查。」，與題目內容無關。範例 PDF 檔名也與 `docs/05_題目集格式與出題指引.md` 不同。
- **做法**：換成與題目相符的答案，並統一兩份文件的範例檔名。
- **驗收**：範例可通過匯入驗證，且內容合理。

### D-11 Dockerfile 的 `uv` 使用 `latest`

- **現況**：README 稱依賴為「已驗證的固定版本」，但 Dockerfile 以 `ghcr.io/astral-sh/uv:latest` 取得 `uv`。
- **做法**：固定 `uv` 映像版本，或在 README 說明只有 Python 套件固定版本。
- **驗收**：重新建置映像不因 `uv` 版本變動而改變行為。

### D-12 `.dockerignore` 列出不存在的檔案

- **現況**：`.dockerignore` 排除 `UI設計書.md`、`專案進度.md`，兩者皆不存在。
- **做法**：移除這兩行，或在建立這些檔案後保留。
- **驗收**：`.dockerignore` 只列出實際需要排除的項目。

### F-44 自動問答測試：小節範圍、召回、引用與延遲

### P-03 多個評審模型評測速度慢：並行數為所有評審共用，④ 同題評審依序執行

- **現況**：
  - 「3 自動問答測試」的「評測回答」（`AutomaticEvaluationService.evaluate`）把每組「題目 × 評審模型」各自當成一個請求，放進同一個 `ThreadPoolExecutor(max_workers=concurrency)`，送出順序是 Q1 的所有評審、Q2 的所有評審……。「評測請求並行數」（預設 3）是所有評審**加總**的上限，所以選 3 個評審、並行數 3 時，同一時間只評一題，評審越多，每題分到的名額越少。
  - 不同評審模型常在不同供應商，速率限制各自計算，共用一個上限不必要地拖慢整體；某個模型被 429 限速或回應很慢時，也會佔住其他模型的名額。
  - 「4 檢索實驗」的 `_run_case` 在同一題內**依序**呼叫每個評審（註解寫明是為了只佔用一個實驗並行名額），3 個評審的評測時間約為單一評審的 3 倍。
- **做法**：
  1. **③ 並行數改為每個評審各自計算**：每個評審模型各有一個執行緒池（或以每模型一個 `Semaphore` 控制），各自最多同時 N 個請求；總並行數為 N × 評審數。進度、停止（F-45 的 `stop_event`）與部分保存行為不變。
  2. **UI 文字**：「評測請求並行數」改為「每個評審的並行請求數」，說明改為「每個評審模型各自同時送出的請求上限；不同模型分開計算」。既有保存值沿用為每評審的數值。
  3. **④ 同題評審改為同時執行**：`_run_case` 內以小型執行緒池同時呼叫各評審，等全部完成再彙總，仍只佔用實驗的一個並行名額（實驗並行數控制的是同時處理的題目數）。或者改為與 ③ 相同的「每評審各自上限」，視實作複雜度決定，並在 UI 說明。
  4. **測試**：以假評審（固定延遲）驗證 3 個評審、每評審並行 N 時，同時進行的請求數達到 3N 且每個模型不超過 N；某一模型全部失敗或很慢時不影響其他模型完成；停止後不再送出新請求、已完成的評分有保存；④ 多評審單題耗時約等於最慢的評審，而非總和。
- **進度**（2026-11-20，`fix/autoqa-q2-retrieval-gaps-v2`，已提交 `015e8ab`）：
  1. ③ `AutomaticEvaluationService.evaluate` 改為每個評審模型各一個 `ThreadPoolExecutor(max_workers=concurrency)`，總並行數為 N × 評審數；停止旗標仍在每個請求送出前檢查，只保存所有評審都完成的題目，進度與部分失敗行為不變。
  2. UI 改為「每個評審的並行請求數」，說明「每個評審模型各自同時送出的請求上限，不同模型分開計算（總並行數 = 此值 × 評審數）」；元件與保存值沿用。

- **未完成**：需用實際索引連續查詢並確認四種策略結果、Evidence 與 Parquet 不重讀；可停止或 timeout 的查詢仍走子程序，不能共用行程內索引快取。所有批次結果視圖是否需顯示快取命中狀態仍待對照任務書確認。
- **驗證進度（2026-11-20）**：`python3 -m compileall -q src tests`、`git diff --check` 與完整測試（561 passed、39 subtests passed）通過；以隔離測試環境啟動管理後台與 portal，兩者分別回傳 HTTP 200，驗證後已停止。

- **驗收**：執行相關測試與完整 `.venv/bin/pytest -q`；確認相同查詢命中、參數與索引版本隔離、bypass 覆寫、損毀降級、WAL 並行讀寫、並發首次載入只讀一次、LRU 釋放及索引熱重載。管理後台與 portal 在新程式重啟後可正常開啟；`temp_docs/` 任務書只留本地，不納入提交。

- **語意快取現況（Goal 20，實作中）**：exact miss 後才對同 scope 做 SQLite/WAL cosine 候選比對。Scope 隔離專案、索引簽章、requested strategy、Chat／Embedding model、回答格式、推理深度、GraphRAG settings hash、prompt 版本、portal defaults、策略參數與安全 guard 版本。新增確定性的數字／單位、英數識別碼、否定、操作動詞、上下文追問及比較／多條件拒絕規則；只用成功且有 Evidence 的 fresh GraphRAG 結果擴增候選，semantic hit 不建立 exact alias 或新候選。
- **啟用政策與設定**：每專案 `query_cache_settings.json` 保存 `off|shadow|serving`，不放在可清除的 cache 目錄，且隨專案匯出；全域 `GRAPHRAG_ENABLE_SEMANTIC_QUERY_CACHE` 預設 false。Shadow 會呼叫 proxy Embedding API、記錄候選與分數但照常 fresh query；serving 另要求明確 threshold／margin／Top-K，有效門檻缺失或無效就不能回傳 semantic hit。Exact cache 先命中時不呼叫 embedding；所有 bypass 同時略過 exact／semantic。
- **風險／限制**：Embedding API 每個 exact miss 至少多一次 request；現有 proxy usage 未提供可靠的 embedding token／費用，因此目前僅記錄 request 次數與延遲。Hard guard 是保守規則但不代表自然語言安全性的證明。沒有真實索引人工標註 holdout，尚不能宣稱候選 threshold 已校準或適合 serving。全域預設與新專案預設維持關閉。
- **測試與目前驗收（2026-11-21）**：新增 Fake embedding／固定向量測試，涵蓋 serving 完整結果重用、scope 隔離、舊 exact-only SQLite migration、cache clear、mode 預設 off、校準門檻 gate、critical hard-negative 與既有 query／experiment／archive regression。完整測試 `570 passed, 49 subtests passed`；未呼叫真實 LiteLLM／Embedding API。隔離的管理後台與 portal 首頁皆 HTTP 200；真實索引與真實入口互動尚未驗收。
- **未完成／下一步**：建立獨立校準集及 holdout（繁中、英文、混合代碼／數字）；critical hard-negative 必須零誤命中，並由專案負責人核定成本與延遲門檻後才能打開 serving。檢視管理 UI、前台提示、檢索實驗 metadata，實際啟動後台與 portal；以可用真實索引做 Shadow 對照與 evidence review。文件已更新於 [回答與圖譜快取機制說明](09_回答與圖譜快取機制說明.md)。
- **Shadow 初步觀察（2026-11-21）**：使用者提供的本機 `temp_docs/queries.jsonl` 共 10 筆，其中 5 筆因 exact hit／舊紀錄沒有觸發 Embedding，另 5 筆各呼叫一次、延遲約 0.9～2.3 秒，尚無 semantic hit。5 次語意查找中 1 次 `no_candidate`、2 次被否定詞逐字規則擋下、1 次把「同時按住兩個按鍵」誤歸多條件、1 次條件尾段因句首／標點差異被拒。hard guard 拒絕的候選沒有記錄 ID／分數，降低可診斷性。另需確認檢索實驗路徑只會以具實際來源 Evidence 的 context 建立候選，不能把只有索引執行 metadata 的 context 當成證據。使用者決定暫不實作，本輪只補文件；細節見[快取機制之語意快取改善計畫](10_快取機制之語意快取改善計畫.md)。
