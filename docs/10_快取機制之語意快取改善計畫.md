# 快取機制之語意快取改善計畫

## 1. 目的與目前決定

本文件記錄語意快取的後續改善工作。依使用者決定，**目前先規劃，不修改程式、不放寬 guard、不啟用 Serving**。現行語意快取維持全域預設關閉；如需查看候選，僅在明確選取的專案使用 Shadow。

語意快取在精確快取未命中後，以 Embedding 找出相似問題候選，再判斷能否重用候選的完整回答與 Evidence。它會減少通過判斷時的 GraphRAG／Chat LLM 工作，但每次實際語意比對仍會呼叫 Embedding API。錯誤重用答案的風險高於多執行一次新查詢，因此任何不確定情況都應拒絕候選。

## 2. 本次 Shadow 紀錄分析

分析資料：本機測試檔 `temp_docs/queries.jsonl`，共 10 筆。該檔是本機測試資料，不納入版本控制或提交。

| 紀錄狀況 | 筆數 | 判讀 |
|---|---:|---|
| 有完整語意欄位且送出 Embedding | 5 | 每筆 `semantic_embedding_calls=1`，延遲約 0.9～2.3 秒，平均約 1.5 秒；皆為 Shadow fresh query，`semantic_cache_hit=false` |
| 沒有呼叫 Embedding | 5 | 多數為 exact hit（`query_cache_type=exact`）；精確快取優先是預期行為。部分舊紀錄沒有新欄位，不能當成 Shadow 執行紀錄 |
| 無同 scope 候選 | 1 | `semantic_cache_reject_reason=no_candidate`；首次語意 miss 常見，該次成功且有 Evidence 後才可能建立候選 |
| 候選被否定詞規則拒絕 | 2 | 「沒有反應／無法操作」等不同措辭被當成極性不同，顯示目前逐字比較否定詞可能過度保守 |
| 候選被多條件規則拒絕 | 1 | 「同時按住兩個按鍵」被 `multi_part_or_comparison` 擋下；「同時」本身不一定代表比較題或多個獨立問題 |
| 候選被條件規則拒絕 | 1 | 近似問題僅有句首／標點差異仍被判為 `condition_mismatch`；條件尾段目前過度依賴原始字串相等 |
| 語意命中 | 0 | 符合 Shadow 不回傳候選的設計；這批資料尚未證明 Serving 安全，也不能單以零 hit 判定功能失效 |

### 2.1 已知可觀察性限制

- `no_candidate` 時沒有候選 ID 或分數，屬正常，因為沒有候選可評分。
- 候選被 hard guard 拒絕時，目前也不會把該候選的 ID／分數寫入查詢紀錄。因而管理者無法從 JSONL 確認是哪一筆候選觸發拒絕，也不容易分辨 guard 誤拒與 embedding 候選品質問題。
- exact hit、bypass、尚未啟用語意功能或舊版 JSONL 紀錄中的欄位缺失，不等同 Embedding 呼叫失敗。判讀時需一起看 `query_cache_type`、`semantic_cache_mode`、`semantic_cache_reject_reason` 及 `semantic_embedding_calls`。
- 每次 Embedding 約 0.9～2.3 秒的這批觀察值只是小樣本，不代表固定延遲或實際費用；proxy 目前未提供可靠的 token／費用資料。

## 3. 改善項目與順序

### S-1：補足候選與拒絕的診斷資訊

讓 Shadow 能檢視「最高候選即使被拒絕」的原因，同時不把問題文字或答案複製到 metrics 欄位。

- 記錄最高候選 ID、分數、候選順位、scope hash、Embedding 延遲與呼叫數。
- 分開記錄 guard 是否通過、guard 拒絕原因、threshold 拒絕、margin 拒絕、無候選、向量／資料錯誤。
- 顯示規則版本及相似度模型版本，讓不同 guard 或 embedding 設定的實驗可區分。
- 即使 guard 拒絕也保留候選 ID／分數；仍不可因此回傳候選答案。
- 驗收：固定向量測試覆蓋每個拒絕分支；JSONL 可判斷最高候選及拒絕原因；既有舊 JSONL 仍可讀；不在新增 metadata 中寫入原始問題、答案或 API key。

### S-2：減少否定／極性規則的同義詞誤拒

目前以否定詞文字清單逐字比較，容易把不同否定表達視為相反意思。不能簡單移除否定防護，因為「可以／不可以」、「接上／拔除」、「啟用／停用」必須維持拒絕。

- 將「句子含否定字」改為判斷否定作用在哪個操作或狀態；區分極性相同但字詞不同，與同一操作被否定／反轉的情況。
- 對「當機／死機／卡死」、「沒有反應／無反應」等汽車／裝置症狀同義詞建立經人工確認的小型詞彙群組；不把「無法操作」自動視作「沒有反應」同義詞，需另行審核語境。
- 英文否定、縮寫與繁中混合用語納入規則測試；分類不確定時維持 miss。
- 驗收：已標註等價改寫可通過 guard；正反操作、雙重否定、否定作用範圍不同的 critical hard-negative 全部拒絕。不可只用單元測試的詞彙例子宣稱 holdout 零誤命中。

### S-3：區分組合操作與多問題／比較題

「同時按住首頁鍵跟返回鍵」是單一的組合按鍵操作；目前規則把「同時」當成多條件訊號，會過度拒絕。

- 移除「同時」單獨觸發拒絕的做法。
- 保留明確比較意圖（比較、差異、哪一個、vs.）與多個獨立請求／子問題的拒絕。
- 將「同時按住 A 和 B」這類單一組合操作與「比較 A、B」／「分別說明 A、B」分開測試。
- 數值／識別碼差異檢查仍需生效。例如 7 秒與 5 秒即使句子含「同時」，仍必須由數值 guard 拒絕。
- 驗收：組合操作不因「同時」一詞被誤擋；比較題、多問題與數值不同案例仍拒絕。

### S-4：正規化條件子句，避免標點與句首造成誤拒

目前條件檢查由條件標記開始，直接比較原文尾段；全形／半形標點或句尾問號不同可能造成 `condition_mismatch`。

- 條件抽取前做 NFKC、大小寫／空白與標點正規化。
- 分開保存條件標記及其條件內容；忽略無語意的句首禮貌詞、主詞補充或標點差異。
- 不得因正規化而移除有語意的數字、單位、車況、時間、警示燈、動作前提或否定。
- 以「同一條件只差標點／主詞」及「冷車／熱車、怠速／行駛、警示燈亮／未亮」等對照組驗證。
- 驗收：純格式差異不造成誤拒；實質條件改變仍必須拒絕；模糊條件在無法安全抽取時 miss。

### S-5：增加 embedding 前的安全預檢與成本評估

部分問題可由原始問題本身識別為不適合語意重用。若能在呼叫 Embedding 前可靠排除，可省下 Shadow／Serving 的額外 API 延遲與費用。

- 評估在 embedding 前對比較題、上下文追問、明確多部分問題與高風險識別碼／條件查詢執行安全預檢。
- 預檢只可採保守規則；不得把無法判斷的問題當成安全候選。
- exact hit 必須維持 Embedding 呼叫數為 0；`off`、bypass、全域總開關關閉及預檢拒絕也應為 0。
- 量測 Shadow 每次 exact miss 的 Embedding latency、呼叫量及 proxy 可提供的 token／費用；比較省下的 GraphRAG／Chat 工作估計。
- 驗收：預檢拒絕均留有明確原因；Shadow 仍保留可用改寫的候選觀察；呼叫量與延遲可由查詢紀錄及 proxy usage 對帳。

### S-6：確保所有查詢入口只索引完整、有來源的結果

- QueryService 必須只用成功完成且 Evidence 非空的 fresh result 建立 semantic entry；精確 cache hit、semantic hit、失敗、取消、部分回答及使用者編輯文字都不得成為新候選。
- 檢索實驗目前以非空 query context 作為候選寫入條件；需確認 context 中含有可核驗的實際來源／Evidence，不能把只有 `index_cache_hit`、載入時間等執行 metadata 的 dict 當成有效 Evidence。
- 確認 semantic source entry 保留 exact source key、canonical query、index scope、原始策略、prompt／embedding schema 版本和完整答案來源；候選損毀、Evidence 欄位不完整時 miss。
- 驗收：一般查詢及實驗路徑都以成功、有來源的 fresh 查詢建立 entry；對 empty context、僅有索引指標、缺失來源、失敗／取消、exact hit、semantic hit 加回歸測試，確認這些情況不新增 semantic entry。

### S-7：建立人工標註資料並校準 Serving

- 使用非敏感、已建圖專案整理繁中、英文及混合代碼／數字的同義改寫與 hard-negative。
- 將資料拆成校準集與獨立 holdout；不得以同一批資料調 threshold／margin 又宣稱 holdout 驗收通過。
- 保留本次觀察到的改寫型態作測試，但由人工逐題核對正確答案、Evidence、操作條件及來源頁碼是否可互換。
- 設定產品錯誤重用容忍度、Embedding 成本／延遲預算、最低有效改寫涵蓋率及負責核准者。
- Critical hard-negative 在 holdout 上必須零語意誤命中；否則不得啟用 Serving。即使通過，也先限定單一專案 opt-in、可立即切回 off。

## 4. Shadow 後續人工測試流程

1. 僅選一個非敏感的已建圖專案，專案模式設 `shadow`；全域開關才可在該受控環境開啟。其他專案保持 `off`。
2. 先送出新問題，確認完成且有 Evidence，讓它成為 canonical semantic candidate；`semantic entries` 應增加。
3. 用同一搜尋策略、模型、回答格式與推理深度提出一個不同措辭的等價問題。確認 `query_cache_type=miss`、Embedding 呼叫數為 1、Shadow 不回傳候選答案，並記錄最高候選與 guard 結果。
4. 逐項改變故障碼／零件號、數字／單位、正反操作、操作動詞、車況／時間條件，確認它們被拒絕。不要一次改多種條件，否則無法知道哪條規則生效。
5. 改測比較題、組合操作及上下文追問，檢查 S-3／上下文預檢是否符合預期。
6. 把 Shadow 候選與 fresh 查詢的答案及 Evidence 人工並排覆核；Shadow `semantic_cache_hit=false` 是預期結果。
7. 將每一組結果標為「可重用」、「不可重用」、「不確定」，記下拒絕／誤拒原因；不確定一律按不可重用處理。

若 `query_cache_type=exact`，表示精確快取先命中，沒有進入語意比對；若 `bypass`，兩種結果快取都被跳過。測試改寫時需確保問題沒有既有 exact entry，且不勾 bypass。

## 5. Serving 前的總驗收門檻

- SQLite 舊 schema migration、WAL 多程序讀寫、TTL、共享容量淘汰、清除、匯出／匯入和損毀降級通過。
- 所有 scope 差異、bypass、`off`、全域總開關關閉及 exact hit 都不得執行語意命中；exact hit 不得呼叫 Embedding。
- Shadow 只記候選、guard、分數及延遲，必須持續 fresh query，不可回傳 semantic result。
- Serving 只有在有效 threshold／margin、人工核准、獨立 holdout critical false-hit 為零，以及成本／延遲預算明確時才可對單一專案啟用。
- Embedding 失敗、資料庫／向量錯誤、模型版本／維度不符、scope 不一致均安全 miss，不得影響正常查詢。
- semantic hit 保留原始候選 ID、Evidence、scope、相似度及新的查詢紀錄；不得建立 exact alias 或語意傳遞候選。

## 6. 暫不處理項目

依使用者本次決定，以上均為改善計畫；本次文件更新不修改 `semantic_query_cache.py`、`querying.py`、`query_cache.py`、後台 UI 或執行環境，也不調整 threshold／margin。Serving 保持關閉，直到後續另行決定實作與校準。
