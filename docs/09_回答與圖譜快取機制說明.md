# 回答與圖譜快取機制說明

本文件說明 GraphRAG 查詢使用的兩層快取：**回答快取（Query Result Cache，含 exact 與 semantic 候選）**與**圖譜快取（In-Memory Index Cache）**。兩者保存的內容、生命週期與命中效果不同，請勿將「圖譜已載入記憶體」解讀成「答案已快取」。語意快取目前仍以 Shadow 觀察及後續改善為主；依目前驗收狀態，不建議啟用 Serving。

## 1. 快取概覽

| 快取 | 保存內容 | 保存位置 | 命中後的效果 | 生命週期 |
|---|---|---|---|---|
| 回答快取 | 已完成查詢的答案、Evidence、查詢資訊等完整結果 | 專案目錄 `cache/query_cache.db`（SQLite/WAL） | 直接回傳舊結果，不重跑 GraphRAG 查詢，也不呼叫生成答案的 LLM | 跨服務重啟保存；預設 30 天過期，並受容量上限管理 |
| 圖譜快取 | GraphRAG 索引表的 DataFrame 與 Arrow Table 參照 | 各服務程序的 RAM | 新問題仍會執行檢索並生成答案，但可重用已載入的索引資料 | 僅存在目前程序；程序重啟後需重新載入，並受 LRU 容量限制 |

兩層的典型流程如下：

```text
提交問題
  ↓
檢查 exact 回答快取
  ├─ 命中：回傳既有答案與 Evidence；不呼叫 Embedding 或回答 LLM
  └─ 未命中／略過
       ↓
     檢查語意快取總開關、專案模式與 bypass
       ├─ off／總開關關閉／bypass／策略不支援：不呼叫 Embedding
       ├─ Shadow：呼叫 Embedding、記錄候選；仍執行新 GraphRAG 查詢
       └─ Serving：呼叫 Embedding；候選全部通過才回傳快取結果
            ↓ miss／Shadow
     檢查圖譜快取並執行 GraphRAG
       ├─ 已載入：重用索引資料
       └─ 未載入：讀取 Parquet 並載入索引
            ↓
     保存 exact 結果；若 fresh 查詢成功且有 Evidence，也建立 semantic 候選
```

Exact 回答快取命中只代表這次問題重用了既有的完整結果；圖譜快取狀態是索引是否仍留在**目前服務程序**的記憶體。Semantic Shadow 找到候選仍會執行新查詢；圖譜快取命中時也仍會執行查詢與 LLM 生成。

## 2. 回答快取

### 2.1 儲存與保存期限

- 每個專案各自保存於 `projects/<project_id>/cache/query_cache.db`，不同專案不共用結果。
- 使用 SQLite WAL 模式與 busy timeout 支援多個程序同時讀寫。
- 預設保存期限為 30 天；到期項目在查詢時視為未命中並刪除。
- 單一專案預設容量上限為 500 MiB。超過上限時，會從最舊的項目開始淘汰。
- 只保存成功完成的查詢結果；失敗的查詢不會作為有效答案快取。
- 刪除專案時，專案目錄與其查詢快取一起移除。

### 2.2 命中條件

系統把完整查詢條件序列化後計算 SHA-256 key。以下條件須一致，才會命中：

- 專案識別碼及索引版本簽章。
- 實際查詢策略（例如 Local、Global、DRIFT 或 Basic）。
- Chat 模型與 Embedding 模型。
- 回答格式、推理深度、GraphRAG 設定檔雜湊及答案 prompt 版本。
- 正規化後的問題文字。

問題正規化使用 Unicode NFKC、合併連續空白並移除首尾空白，再轉為小寫。因此全形／半形差異、空白差異及英文字母大小寫差異可被合併。例如 `P0300 如何檢修` 與 `Ｐ０３００　如何檢修` 正規化後相同。

精確快取不是語意比對。標點、詞彙、句序或問題條件不同，通常不會命中。專案另有**語意候選快取**，但全域預設關閉、各專案預設 `off`；必須管理員逐步啟用並設定校準過的門檻才會服務命中（見第 4.5 節）。

### 2.3 命中後的行為

命中時，系統回傳保存的答案及 Evidence，不會再次呼叫 GraphRAG 搜尋，也不會呼叫查詢流程中的 LLM（包括自動策略路由、回答生成及相關改寫）。系統仍會為這次操作產生新的查詢紀錄，保留本次問題與來源等資訊，並標示 `query_cache_hit`。

快取命中顯示的是上一次成功查詢的結果。若原始手冊、引用或答案有問題，必須使用「略過快取」重新查詢，否則會繼續看到原結果。

### 2.4 索引版本與失效

索引簽章優先取自成功建圖紀錄中的 `run_id` 或 `completed_at`；缺少可用紀錄時，使用 GraphRAG 輸出 Parquet 檔名、最後修改時間與大小計算簽章。索引版本改變後，舊版本的答案不會被新版本查詢命中。

新舊版本的磁碟快取可能在 TTL 或容量淘汰前同時存在；它們因簽章不同而互相隔離。若需立即移除，可使用管理後台的「清除本專案快取」。

## 3. 圖譜快取

### 3.1 載入內容與策略

圖譜快取由 `GraphIndexManager` 管理，依 `(project_id, index_signature)` 識別載入版本，主要包含：

- entities
- relationships
- communities
- community_reports
- text_units
- 可選的 covariates

載入時使用 PyArrow Parquet memory map，並保留 Arrow Table 參照；同時轉換為 GraphRAG 查詢所需的 typed DataFrame。Local、Global、DRIFT、Basic 行程內查詢可重用這些資料。查詢改寫、Evidence 與重複引用解析也可使用已載入的 text_units，減少重複讀取。

memory map 用來改善載入方式與降低部分峰值記憶體壓力，不代表整份圖譜永遠不占 RAM，也不保證零複製。大型圖譜仍可能占用大量記憶體，請依主機容量設定常駐專案數。

### 3.2 容量、淘汰與重新載入

- 以 LRU（最近最少使用）控制常駐專案數；新專案超過容量時，淘汰最久未使用的索引並嘗試回收記憶體。
- 一般使用者入口預設上限為 2 個專案；管理後台預設為 1 個專案。
- 可用 `GRAPHRAG_MAX_LOADED_PROJECTS` 調整每個服務程序的上限，最小為 1。
- 同一專案的並發首次載入會共用專案鎖，避免同時重複載入。
- 同一專案索引簽章改變時，該程序會移除舊版本並重新載入。
- 服務程序重新啟動會清空該程序的圖譜快取；第一次後續查詢會再載入。

每個服務程序各有自己的 RAM 快取。管理後台載入圖譜，不代表另一個 portal 程序也已載入；若兩個入口分開執行，同一專案可能各自占用一份記憶體。反過來說，清除一個程序的圖譜快取不會直接釋放另一個程序中的副本。

### 3.3 停止與逾時查詢的限制

支援停止或受到 timeout 管理的查詢，以及 Agentic 查詢，仍使用隔離子程序以維持既有的取消與逾時行為。這些查詢不會共用 `GraphIndexManager` 的行程內圖譜快取；查詢紀錄中的 `index_cache_hit` 可能為 false，或載入時間為 null。這不影響回答快取命中後直接回傳既有結果的行為。

## 4. 管理與使用者操作

### 4.1 管理後台：清除與狀態

在專案管理／建圖頁開啟專案後，可看到：

- **圖譜已常駐記憶體／圖譜尚未載入記憶體**：表示管理後台目前這個服務程序是否保留該專案的圖譜索引。尚未載入是正常狀態，通常第一次符合條件的行程內查詢後才會載入。
- **本專案查詢快取：N 筆**：回答快取資料庫中目前記錄的項目數；這與圖譜是否常駐無關。
- **清除本專案快取**：清除該專案的磁碟回答快取，並從管理後台目前程序釋放該專案的圖譜快取。

若看到「查詢快取資料庫損毀」，可按清除按鈕移除損毀資料庫並重新建立。清除不會刪除索引、PDF、專案設定或既有問答紀錄，也不會保證釋放其他服務程序內的圖譜副本。

### 4.2 管理後台：單次問答

在「2 問答測試」輸入問題並送出，預設允許使用回答快取。查詢資訊會在命中時顯示「來自快取」及原始耗時。勾選「略過快取重新生成」後送出，會跳過回答快取、重新執行檢索與生成，並以新成功結果更新相同條件的快取項目。

### 4.3 設定各專案的前台查詢預設值

在管理後台「0 專案與連線設定」選擇專案後，展開「前台使用者預設查詢設定（依專案）」並設定：

- **預設搜尋策略**：Auto、Local、Global、DRIFT 或 Basic。前台目前不提供 Agentic Search 實驗策略。
- **預設回答模型**：指定可用 Chat 模型，或選「使用全域預設」跟隨共用連線設定。模型後續若從可用清單移除，前台會退回全域預設。
- **預設推理深度**：low、medium 或 high；只對支援 reasoning 的模型生效。
- **預設回答格式**：單句、條列、單段、多頁報告或精簡格式等。

按「儲存前台預設設定」後，設定會寫入該專案的 `portal_defaults.json`，不同專案各自保存。舊專案沒有此檔時會使用 Local、全域預設模型、medium、Single Paragraph。一般使用者入口每次送出問題都依目前選定專案載入這些值，不必重啟 portal。建立或匯入專案後也可在第 0 頁設定。此檔屬於專案設定資料，專案匯出時會一併保存，不受「包含／略過快取」選項影響。

管理後台的「2 問答測試」與一般使用者入口若要共用回答快取，兩邊必須選用相同的策略、模型、推理深度、回答格式、專案與索引版本。管理後台單次問答預設策略是 Auto；前台專案預設策略是 Local。若管理後台選 Auto、前台選 Local，即使 Auto 最後路由到 Local，快取 key 仍不同，不會互相命中。要共用 Local 查詢結果，請將管理後台查詢方法也切換為 Local，或將該專案前台預設改成 Auto。

### 4.4 一般使用者入口

一般入口按選定專案的前台預設使用回答快取。若目前只有一個已建圖且啟用的專案，頁面會自動選取該專案並啟用「送出問題」與「重新生成」按鈕；若有多個可查詢專案，請先從「車型／專案」下拉選擇。若沒有可查詢的專案，頁面會提示管理者確認專案已完成建圖且啟用。命中時回答資訊會顯示快取提示及原耗時，並列出本次實際使用的策略與模型。按「重新生成（略過快取）」會強制重新檢索與生成，完成後用新結果取代相同條件的快取項目。

### 4.5 自動問答與檢索實驗

- **3 自動問答測試**：有「略過查詢快取（強制重跑）」選項，預設不略過。進行品質評估或需要每次實際執行檢索時，建議勾選，避免既有答案掩蓋新的執行結果。
- **4 檢索實驗**：同樣有略過選項，預設勾選，避免快取結果扭曲延遲及策略比較。若要特別測試重複問題快取，取消勾選。
- bypass 只略過答案結果快取；符合條件的行程內查詢仍可使用圖譜快取。若要測圖譜首次載入，需清除目前服務程序的圖譜快取或重啟對應服務。

### 4.6 語意候選快取（全域預設關閉）

語意快取只在 exact miss 後執行。符合 serving 條件時會重用相似問題先前的**完整成功結果**（回答、Evidence、引用與來源資訊），不執行本次 GraphRAG 搜尋或 Chat LLM；但會呼叫一次 Embedding API，因此不是零 API 呼叫。Embedding 失敗、資料損毀或任何檢查未通過時會安全回到一般查詢。

管理員在「0 專案與連線設定」選擇專案，展開「前台使用者預設查詢設定（依專案）」下方的「語意快取」設定模式：

- **關閉（off）**：不呼叫 Embedding、不做語意候選查找；精確快取照常工作。
- **觀察（Shadow）**：exact miss 時呼叫 Embedding、檢查候選並把分數／拒絕原因記到 query log，但仍執行新 GraphRAG 查詢並回傳新結果。這會增加 Embedding 成本與延遲。
- **服務（Serving）**：所有 scope、硬性防護、相似度 threshold 與候選 margin 均通過時，回傳候選的完整結果。畫面會標示「語意相似快取」與相似度。

模式保存在專案根目錄 `query_cache_settings.json`，不是 `cache/` 子目錄；清除答案快取不會重設模式，專案匯出／匯入會保存此設定。新專案及舊專案缺少檔案時都預設 `off`。管理員停止語意快取可立即切換 `off`；全域開關關閉也會強制停用所有專案的 shadow／serving。

**全域開關不會把所有專案切成啟用狀態**：即使服務環境的 `GRAPHRAG_ENABLE_SEMANTIC_QUERY_CACHE=true`，專案模式為 `off` 的專案仍不會呼叫 Embedding。只有「全域開關開啟＋該專案模式為 Shadow／Serving＋此請求 exact miss 且未 bypass」才可能進入語意查找。管理後台與 portal 是不同程序；若兩邊都要觀察同一專案，兩個服務程序都要取得相同的全域環境變數並重新啟動。

語意候選應由**實際 fresh 執行成功且具有可核驗 Evidence／來源**的查詢建立；語意 hit、失敗或缺少 Evidence 的結果不得作為候選。一般 `QueryService` 路徑有檢查 Evidence；檢索實驗路徑的候選資格仍列為待改善項目，需確認它不會把只有索引命中／載入時間等 metadata 的 context 誤當 Evidence。詳見[改善計畫 S-6](10_快取機制之語意快取改善計畫.md)。第一次 Shadow 問題常見 `no_candidate`，因為當時還沒有候選；該次查詢完成且有 Evidence 後，後續不同問法才有可能比對。`semantic entries=0` 時先確認上一筆查詢成功並有 Evidence。`query_cache_type=exact` 表示 exact 已先命中，該請求不會觸發 Embedding；`bypass` 則同時略過 exact／semantic。要實際觸發 Shadow，使用同一專案、相同搜尋策略與模型設定、從未精確快取過的問題，不要勾選 bypass。

Shadow 模式在沒有校準 threshold／margin 時仍可計算候選及 guard 結果，但一定 fresh query；`uncalibrated_threshold` 不代表 provider 失敗。`no_candidate` 表示該 scope 沒有候選；數字／單位、識別碼、極性、動作、條件或問題型態 guard 拒絕時，現在的實作可能只記拒絕原因而沒有候選 ID／分數。此可觀察性限制及 guard 誤拒改善已列於[語意快取改善計畫](10_快取機制之語意快取改善計畫.md)。

目前 production embedding 使用既有 LiteLLM OpenAI-compatible proxy 的 `/embeddings` 端點。每次 exact miss 至少多一次 Embedding request；查詢紀錄會寫入呼叫數、模型及延遲。現有連線層未提供可靠的 embedding token／費用資訊，因此目前不能聲稱已量出實際費用。Shadow 同樣會呼叫 Embedding API。自動問答／檢索實驗 `bypass_cache=true` 時，會一併略過 exact 與 semantic lookup。

Serving 的門檻不提供產品預設值。需在服務啟動環境自行設定且重新啟動：

```dotenv
GRAPHRAG_ENABLE_SEMANTIC_QUERY_CACHE=true
GRAPHRAG_SEMANTIC_QUERY_CACHE_THRESHOLD=<已校準的 0 到 1 間數值>
GRAPHRAG_SEMANTIC_QUERY_CACHE_MIN_MARGIN=<已校準的 0 到 1 間數值>
GRAPHRAG_SEMANTIC_QUERY_CACHE_TOP_K=5
```

未設定或值無效時，serving 不會回傳語意候選。Shadow 可在 threshold／margin 尚未校準時記錄候選分數，但仍會做 fresh query。不要直接照抄範例相似度值；應以繁中、英文及混合代碼問題分開建立校準集與保留 holdout，critical hard-negative 必須零誤命中。尚未完成真實索引的 holdout 校準前，不要開啟 serving。

硬性防護會拒絕數字／單位、英數識別碼、否定極性、操作動詞不同的問題，並排除上下文追問、比較及多條件問題。這是保守的 deterministic guard，不保證能辨識所有隱含條件；任何高風險使用情境都應維持 `off` 或 `shadow`。語意 hit 不會建立新 exact alias，也不會以 hit 結果擴增 semantic index，只有 fresh 成功查詢且有 Evidence 才建立候選，避免命中鏈造成漂移。

目前 Shadow 紀錄曾出現以下過度拒絕跡象：否定詞清單逐字比較，把「沒有反應／無法操作」當作極性不同；「同時按住兩個按鍵」被當成多條件；條件尾段逐字比較，句首／標點不同仍拒絕。這些現象是拒絕率偏高的候選問題，不代表應直接移除防護或放寬門檻。改善計畫要求先補齊被拒候選的 ID／分數及 guard 詳細原因，再用人工標註的等價改寫和 hard-negative 回歸驗證。

## 5. 查詢紀錄欄位

新查詢紀錄包含以下快取欄位：

| 欄位 | 意義 |
|---|---|
| `query_cache_hit` | 此次是否直接重用已保存的完整查詢結果。true 時不重跑搜尋與答案生成。 |
| `query_cache_type` | `exact`、`semantic`、`miss` 或 `bypass`。缺少此欄位的舊 JSONL 紀錄仍可讀取。 |
| `semantic_cache_hit` | 此次是否重用語意候選；語意命中時 `query_cache_hit` 仍為 false。 |
| `semantic_cache_score`／`semantic_cache_threshold` | 命中或候選分數及本次判定門檻；shadow 用於離線分析。 |
| `semantic_cache_candidate_id`／`semantic_cache_scope_hash` | 命中候選識別碼及隔離 scope 雜湊，不包含原始問題文字。 |
| `semantic_cache_mode`／`semantic_cache_reject_reason` | 本專案模式及沒有命中的原因。 |
| `semantic_embedding_latency_ms`／`semantic_embedding_model`／`semantic_embedding_calls` | Embedding request 延遲、模型與次數；不代表已取得 token 或費用。 |
| `index_cache_hit` | 此次行程內查詢是否重用目前程序已載入的圖譜資料。 |
| `index_load_sec` | 載入圖譜索引所花時間；已命中時通常為 0，無法量測或走隔離子程序時可能是 null。 |

回答快取命中時，`index_cache_hit`／`index_load_sec` 可能保留原始成功查詢的索引載入資訊；應以 `query_cache_hit` 判斷此次是否重用完整答案。舊版 JSONL 紀錄沒有這些欄位時仍可載入。

## 6. 設定參數

以下變數可在服務啟動環境中設定。未設定時使用表列預設值：

| 環境變數 | 預設值 | 用途 |
|---|---:|---|
| `GRAPHRAG_ENABLE_QUERY_CACHE` | `true` | 啟用／停用磁碟回答快取。接受 `0`、`false`、`no`、`off` 作為停用值。 |
| `GRAPHRAG_QUERY_CACHE_TTL_SECONDS` | `2592000`（30 天） | 回答快取的存活秒數。 |
| `GRAPHRAG_QUERY_CACHE_MAX_BYTES` | `524288000`（500 MiB） | 單一專案回答快取資料庫的容量上限。 |
| `GRAPHRAG_ENABLE_INDEX_CACHE` | `true` | 啟用／停用行程內圖譜快取。接受 `0`、`false`、`no`、`off` 作為停用值。 |
| `GRAPHRAG_MAX_LOADED_PROJECTS` | 管理後台 `1`；一般入口 `2` | 每個服務程序最多保留的專案圖譜數。 |

環境變數須在服務啟動前設定；修改後需重啟對應服務才會套用。停用回答快取不會自動停用圖譜快取，兩者可分別控制。

## 7. 匯出、匯入與資料保存

專案匯出時，回答快取資料庫與 `graphrag/cache/` 預設不包含在匯出檔，以控制檔案大小。若在匯出確認對話框選擇包含快取，程式會同時納入 `graphrag/cache/` 與專案 `cache/`（其中包含 `query_cache.db`）；雖然對話框文字著重 GraphRAG LLM 快取，實際開關涵蓋兩個目錄。圖譜索引輸出仍會依匯出規則保存。

匯入專案後，若匯出時未包含快取，回答快取資料庫不會隨專案帶入；若選擇包含快取，則會一併匯入。無論是否匯入磁碟回答快取，圖譜索引都需在各服務程序中載入至 RAM。

## 8. 注意事項與故障排除

1. **答案不是最新內容**：檢查是否顯示「來自快取」；勾選略過快取重新生成，或清除本專案快取。
2. **改寫問法未命中**：目前只做字串正規化，不做語意相似度比對；需使用相同正規化文字及查詢條件。
3. **顯示圖譜尚未載入記憶體**：表示目前入口程序沒有常駐索引，不代表索引不存在或建圖失敗。第一次行程內查詢、服務重啟、索引更新或 LRU 淘汰後都可能顯示此狀態。
4. **查詢仍很慢**：首次載入大型 Parquet 可能需要時間；停止／timeout／Agentic 查詢不使用行程內快取；重複問題若回答快取 key 不同也會執行完整查詢。
5. **記憶體使用偏高**：降低 `GRAPHRAG_MAX_LOADED_PROJECTS`，或按清除按鈕釋放目前管理後台程序中的圖譜參照。大型圖譜仍需足夠 RAM。
6. **重新建圖後仍擔心舊結果**：索引簽章會隔離新版查詢；若成功建圖紀錄或輸出時間戳異常，可清除本專案快取後重試。
7. **查詢快取資料庫異常**：快取讀寫失敗會盡量降級為一般 GraphRAG 查詢；管理頁如顯示資料庫損毀，使用清除功能重建。
8. **多入口或多容器**：SQLite 回答快取可在共享專案目錄間共用；圖譜 RAM 快取依程序各自存在，容量上限也是每個程序分別計算。專案的語意模式設定在共享專案路徑；服務端全域開關與校準環境變數需各程序一致。
9. **語意快取誤用風險**：正式 serving 前先用固定 holdout 驗證數字／單位、代碼、極性、動作與情境 hard negative；沒有零誤命中證據時只用 off／shadow。Shadow 有 API 成本但不會回傳候選舊答案。

## 9. 驗收方式

可用已建圖專案依序驗證：

1. 單次問答第一次執行後記錄 `query_cache_hit`、`index_cache_hit`、`index_load_sec` 與耗時。
2. 相同問題與相同條件再執行，確認 `query_cache_hit=true`，結果含相同答案與 Evidence，且不再呼叫回答 LLM。
3. 改變大小寫、全半形或空白，再確認 exact 正規化命中；若語意 cache 未啟用，換句話說預期不會命中。
4. 勾選略過回答快取，確認重新檢索並更新結果。
5. 以不同問題測圖譜快取：第一次載入後再查新問題，確認 `index_cache_hit=true`；清除／重啟後應再次載入。
6. 變更策略、模型、回答設定或索引版本，確認舊回答不會被錯誤重用。
7. 對照兩個入口程序各自的圖譜狀態，確認 RAM 快取不跨程序共享。

10. 以 Mock／Fake embedding 驗證 off／shadow／serving、threshold／margin、scope 隔離及各 hard negative；測試不得連真實 API。確認 exact hit 的 embedding 呼叫數為 0，bypass 同時略過兩種結果快取。
11. 對固定 holdout 報告各類 critical false-hit、改寫候選命中率、拒絕率、Embedding request 數與延遲；critical false-hit 未達零前不得開 serving。
