# 改善計畫

本文件追蹤專案的改善項目。新增、調整項目時，同步更新「狀態總覽」與對應項目的現況、做法及驗收標準；新發現的問題也記錄在此。

項目完成後，在狀態總覽的「結果」欄寫一句做法與驗收結果，並附上 commit hash，然後刪除下方該項目的細節段落。完整改動可由 commit 查詢。

狀態：`待辦`、`進行中`、`待確認`（需先決定方向）、`完成`、`不處理`

## 文件與設定問題

### D-01 本機 `.env` 只讀取 API Key

- **現況**：README 與 `docs/安裝與啟動.md` 表示 `.env` 可設定 `GRAPHRAG_API_BASE`、`GRAPHRAG_CHAT_MODEL`、`GRAPHRAG_EMBEDDING_MODEL`。程式只以 `dotenv_values` 讀取 API Key（`_dotenv_api_key`）與 Cloudflare Access 憑證（`_cloudflare_access_headers`），未呼叫 `load_dotenv`，因此本機 `.env` 的 Base URL 與模型不會生效。Docker 使用 `--env-file` 時不受影響。
- **做法（擇一）**：
  - A. 程式改為從 `.env` 讀取全部四個設定，與文件一致，並補測試。
  - B. 文件改為說明本機 `.env` 只提供 API Key，其餘設定請用環境變數或「0 專案與連線設定」的連線設定區塊。
- **驗收**：本機只放 `.env` 時，「0 專案與連線設定」的連線設定區塊顯示的 Base URL 與模型與文件描述一致。

### D-02 連線設定讀取優先順序不一致

- **現況**：API Key 現為 `PROJECTS_ROOT/.connection.json` → 環境變數 → `.env`，Base URL 與模型為 `.connection.json` → 環境變數，三者都以已儲存設定優先，差別只剩 `.env` 僅供 API Key（見 D-01）。在後台儲存過一次後，再改環境變數不會生效；`docs/交接紀錄.md` 仍寫舊順序（環境變數優先），`docs/安裝與啟動.md` 未列出順序。
- **做法**：確認「已儲存設定優先」是否為預期行為，再同步測試與 `docs/安裝與啟動.md`、修正交接紀錄。與 D-01 一起處理。
- **驗收**：`tests/test_connections.py` 涵蓋四個設定在三種來源下的優先順序；文件明列順序。

### D-03 README Linux 同時啟動兩入口會搶連接埠

- **現況**：README「非 Docker 啟動方式」的 Linux 指令沒有為兩個入口指定不同連接埠，兩者都使用預設的 7860，後啟動者會失敗。Windows 指令則已分開使用 7860 與 7861。
- **做法**：Linux 管理後台指令加上 `GRADIO_SERVER_PORT=7861`。
- **驗收**：照 README 在 Linux 同時啟動兩入口皆成功。

### D-04 使用指南與策略文件的指標說明過時

- **現況**：`docs/使用指南.md` 常見狀況提到「Recall／MRR」，但「4 檢索實驗」顯示的是 Evidence Hit Rate、Evidence Precision、Document Hit Rate；Recall／MRR 只存在於已隱藏的舊分頁。`docs/檢索實驗與策略參數.md` 稱「沒有排序後的來源排名」時標示不可計算，但程式註明這三個指標不使用排名。
- **做法**：改寫為目前三個指標，以及實際的「不可計算」條件（缺 Gold 頁碼、策略來源無法映射，例如 Global 社群報告）。
- **驗收**：文件中的指標名稱與「4 檢索實驗」摘要表欄位一致。

### D-05 README 常見問題提到已隱藏的勾選框

- **現況**：README「如何降低開發測試成本」建議「不要勾選重新執行系統回答」，但該勾選框位於隱藏的「自動評測（已整合）」分頁，使用者看不到。
- **做法**：改為對應「3 自動問答測試」／「4 檢索實驗」現行流程的說法（回答與評測分開執行，評測只使用既有回答）。若 F-01 移除隱藏分頁，一併確認。
- **驗收**：README 提到的控制項都能在介面上找到。

### D-08 交接紀錄搬移後連結失效、欄位名稱過時

- **現況**：第 3 行失效的相對連結已隨 D-06 修正。內文的題目集欄位 `reference_answer`、`answer` 與現行格式 `expected_answer` 不同，現行匯入會拒絕舊欄位，尚未處理。
- **做法**：在欄位說明旁註明已由 `docs/題目集格式.md` 取代。
- **驗收**：連結可開啟；讀者不會依舊欄位建立題目集。

### D-09 範例題目集答案為佔位文字

- **現況**：`docs/檢索實驗格式範例.json` 兩題的 `expected_answer` 都是同一句「先確認設備已關閉，準備指定工具，並依序完成安全檢查。」，與題目內容無關。範例 PDF 檔名也與 `docs/題目集格式.md` 不同。
- **做法**：換成與題目相符的答案，並統一兩份文件的範例檔名。
- **驗收**：範例可通過匯入驗證，且內容合理。

### D-10 README 安裝指令未指定 Python 版本

- **現況**：README 使用 `python3 -m venv`，在 `python3` 為 3.10 的環境會因需求 `>=3.11` 而安裝失敗。`docs/安裝與啟動.md` 則寫死 `python3.12`。
- **做法**：兩份文件統一寫為 `python3.12`（或 `python3.11`），並註明最低需求與版本檢查方式。
- **驗收**：兩份文件的安裝指令一致。

### D-11 Dockerfile 的 `uv` 使用 `latest`

- **現況**：README 稱依賴為「已驗證的固定版本」，但 Dockerfile 以 `ghcr.io/astral-sh/uv:latest` 取得 `uv`。
- **做法**：固定 `uv` 映像版本，或在 README 說明只有 Python 套件固定版本。
- **驗收**：重新建置映像不因 `uv` 版本變動而改變行為。

### D-12 `.dockerignore` 列出不存在的檔案

- **現況**：`.dockerignore` 排除 `UI設計書.md`、`專案進度.md`，兩者皆不存在。
- **做法**：移除這兩行，或在建立這些檔案後保留。
- **驗收**：`.dockerignore` 只列出實際需要排除的項目。

### F-20 搜尋策略優化與受限 Agentic Search

- **現況**：既有「自動」模式只根據問題文字選擇一種 Local／Global／DRIFT／Basic，沒有取得搜尋結果後檢查來源或補搜。答案錯誤也可能來自前處理、索引、召回、證據或生成階段，不能只以策略分類解釋。
- **任務書**：[`搜尋策略優化與擴充任務書.md`](搜尋策略優化與擴充任務書.md)。
- **Phase 0 進度**：已新增[策略錯誤分析範本](策略錯誤分析範本.md)，定義題型、答案／Evidence 等級、錯誤歸因順序及比較控制條件。使用者提供 Samsung S25 手冊副本（現為 `projects/Samsung`，測試資料不納入 Git）。專案已建圖，題目集 30 題均有參考答案與 Gold Evidence，共 32 個文件／頁碼標註且全部可在來源 Metadata 中找到；題集當時為 PENDING（現 30 題已回答並完成評測），題型以單本手冊事實查找為主，沒有無答案、衝突或跨文件題，因此可做窄範圍試測，不能代表汽車維修或完整題型表現。既有 3 筆 Auto 紀錄的 Evidence Hit Rate 為 2/3、Document Hit Rate 為 3/3、平均頁面 Evidence Precision 為 6.7%、平均延遲 21.072 秒；樣本太少，答案品質尚未完成雙人覆核。固定策略 pilot 的 Local 呼叫收到 HTTP 401；Global 雖回傳 canned「不知道」，query log 顯示模型請求也全數 401，故不計為有效結果，並已停止後續 API 請求。Basic／DRIFT 固定策略基線待有效 API Key 後重跑。
- **Phase 1 進度**：Agentic 查詢每步現在使用 `SearchStepResult`／`SearchEvidence`，記錄查詢、計畫目的、答案、原始 context、來源類型、錯誤與耗時；查詢紀錄保存模型、推理深度、回應格式、prompt 版本、GraphRAG 設定檔 SHA-256、模型呼叫數、搜尋步數與停止原因。Evidence `rank` 明確是顯示順序，不當作相關性分數。舊查詢歷史仍可讀；但 API adapter 未提供 token 用量，成本估計保持未知，普通 GraphRAG 查詢的內部模型呼叫數也未知。Phase 2 離線安全測試已覆蓋嚴格計畫／評估 schema、重複補搜抑制、無 Evidence 拒答、來源衝突指示、executor 例外及預算耗盡；真實模型與索引驗證仍待資料。
- **已做**：新增受限 Agentic Search 模組與單題查詢入口。Planner 只可選 GraphRAG 四種既有方法；先執行一次搜尋，再依檢索結果及 Evidence 評估是否需要一次補搜，最後以來源證據整合答案。每題最多兩次 GraphRAG 搜尋，總流程上限 300 秒；模型輸出需通過方法白名單及查詢長度驗證。無 API Key 或規劃無效時回退 Local。最終回答的來源 ID 會對齊 EvidenceService 實際顯示的 ID，未能映射的引用明確標記。Agentic Search 已提供單題查詢、檢索實驗及自動問答測試選項；自動問答沿用每題執行及既有並行數設定，UI 提示額外模型呼叫與延遲。

### F-22 自動策略找不到答案時依序嘗試其他檢索方式

- **現況**：「自動」目前只由回答模型挑選 Local／Global／DRIFT／Basic 其中一種策略；該策略沒有找到答案時不會繼續搜尋。
- **目標**：先執行自動路由選出的策略；若答案判定為未找到，再逐一嘗試尚未使用的其他策略，直到找到可接受答案或四種策略都已測過。每種策略每題最多執行一次。
- **待設計**：明確定義「找到答案」的判定方式（例如獨立答案評估器與拒答／無依據訊號）；定義 fallback 次序及四種皆未找到時的回傳內容。執行額外策略會增加延遲及模型成本，需在 UI 與紀錄中呈現實際嘗試策略。
- **驗收**：第一個策略無答案、後續策略找到答案時停止並回傳成功策略的答案；四種皆無答案時最多執行四次且回傳清楚的未找到結果；成功時不再執行其他策略；逐題紀錄保存嘗試順序、各策略結果與停止原因，既有固定策略及單次自動路由行為保持相容。

### F-37 引用編號與手冊頁碼混淆

- **現況**：手冊頁面文字開頭印有頁碼（如 `設定\n171\n…`），Text Unit 的 `human_readable_id` 又幾乎等於「頁碼 − 1」，模型會把頁碼寫進 `[Data: Sources (…)]`。Samsung S25 30 題中有 6 題如此。F-36 的頁碼備援只處理對不到記錄的情況；若頁碼剛好也是另一筆已檢索 ID，會被當成正確引用，目前無法偵測。
- **做法**：送給回答模型的 Sources 編號改用不像頁碼的格式（例如 Agentic Search 已用的 `E1`），回答後再對回 Evidence；需評估 GraphRAG context 組裝與各專案 prompt 的改動範圍。
- **驗收**：既有題目集重新查詢後，引用都能直接對回 Evidence，不需頁碼備援；相關測試通過。

### F-40 「4 檢索實驗」顯示與匯出分離答案及來源

- **現況**：F-36 只改了「3 自動問答測試」的結果表與匯出。④ 的評審、EM／F1 與來源分數已用純答案與程式比對，但表格的「系統回答」仍含引用，「來源文件」只列文件名稱，匯出也沒有分開的欄位。
- **做法**：`_experiment_question_cells` 比照 ③ 顯示純答案與系統引用／正確來源的文件及頁碼，匯出新增 `raw_system_answer`、`system_answer_sources` 對應欄位；同步更新表頭測試。
- **驗收**：④ 三張逐題表與匯出的答案不含引用，來源可逐題對照；相關測試通過。

### F-41 無頁碼的正確來源在單一文件專案等於送分

- **現況**：正確來源沒有標頁碼時，只要引用到同一份文件，`source_score` 就給 100%。F-38 只處理有頁碼的情況，單一文件專案仍等於送分。Samsung S25 題目集都有標頁碼，不受影響。
- **做法**：決定單一文件專案遇到無頁碼正確來源時改為「不適用」或其他處理，並與 `project_document_only_score` 一起調整。
- **驗收**：單一文件專案不會因無頁碼正確來源得到 100%；多文件專案行為不變；相關測試通過。
