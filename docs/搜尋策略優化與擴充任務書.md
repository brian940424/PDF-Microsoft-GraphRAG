# 搜尋策略優化與擴充任務書

## 1. 目標與範圍

在既有 Microsoft GraphRAG 索引、查詢方法與 Evidence 流程上，改善「自動」查詢的答案正確率與可追溯性，並評估新增 Agentic Search。新策略應能依問題規劃一個或多個受控搜尋步驟，讀取檢索證據、判斷尚缺資訊，必要時追加搜尋，最後只根據可檢查的證據回答。

本任務先完成基準、設計與受限原型，再依評測結果決定是否成為正式查詢選項。新增 Agentic Search 不代表要取代 Microsoft GraphRAG 的索引、Text Units、實體／關係、社群報告或既有 Local／Global／DRIFT／Basic 查詢。

### 目標

- 找出目前答案錯誤主要來自路由、召回、索引內容、證據整合或回答生成的哪一階段。
- 將目前只看問題文字的一次性策略分類，提升為可以依檢索結果作有限次調整的查詢編排流程。
- 保留來源文件、頁碼、Text Unit 及 Evidence 對應；不因加入 Agent 而犧牲可追溯性。
- 讓新策略可用同一題目集和現有實驗流程，與固定策略及目前「自動」模式直接比較。
- 對模型呼叫數、搜尋輪數、總耗時與錯誤回退設上限，成本可預期且過程可重現。

### 範圍

- 查詢策略及編排器、路由與查詢計畫、證據檢查、停止條件、結果記錄。
- 接入單題問答及檢索實驗；視評測結果再接入自動問答測試。
- 必要的結果 schema、UI 狀態、文件及回歸測試。

### 不在本任務範圍

- 更換 Microsoft GraphRAG 索引後端或重建知識圖譜架構。
- 讓模型執行任意 Python、Shell、Cypher、SQL、檔案系統或網路工具。
- 一次移植所有向量、全文、Hybrid、Reranker、Greedy DFS 或其他 Agent 框架。
- 在沒有人工標註基準的情況下，宣稱單一新策略已普遍提高正確率。

## 2. 現況與程式落點

### 2.1 目前自動查詢流程

`StrategyRouter` 將問題文字與 Local／Global／DRIFT／Basic 的英文說明送給回答模型，要求模型輸出策略名稱及繁體中文原因。接著 `QueryService.ask()` 將所選方法交給 GraphRAG 查詢工作程序執行。路由模型不會取得檢索結果，也不會確認證據是否涵蓋問題；策略判定失敗則固定回退 Local。

因此目前「自動」是單次的問題分類，不是會根據檢索品質調整搜尋的 Agent。模型的路由依據只有問題文字和 prompt 中的策略定義，沒有文件內容、索引品質或候選 Evidence。

### 2.2 目前可沿用的能力

- `strategy_routing.py`：目前策略分類及回答模型呼叫。
- `querying.py`：單題查詢、方法選擇、結果持久化與查詢紀錄。
- `graph_query_worker.py`：透過 GraphRAG 3.2 查詢 Local／Global／DRIFT／Basic，並將回答及 query context 序列化回傳。
- `evidence.py`：從 query context 解析 Text Unit 或 Global community report；可取得的來源 Metadata 包含文件、頁碼與原文。
- `retrieval_experiments.py`、`retrieval_evaluation.py`：固定題目集、多策略組別、答案評測、Evidence Hit Rate／Precision／Document Hit Rate。

目前 GraphRAG CLI 查詢工作程序對可用原生方法有明確白名單。Agentic Search 應新增在應用層，透過此白名單呼叫現有策略，不應讓模型直接組裝任意 CLI 命令。

### 2.3 現有策略適用性與限制

| 策略 | 適合問題 | 可能的限制與失敗方式 |
| --- | --- | --- |
| Local | 特定零件、系統、症狀、規格、維修步驟；需要實體周邊關係及原文片段 | 問題中的關鍵概念未抽成 Entity、同義詞未連結或關係缺失時，可能召回不足；可能因實體映射偏差帶入錯誤鄰接脈絡 |
| Global | 跨語料主題、整體摘要、趨勢、類型歸納 | 仰賴 Community Reports 的涵蓋與摘要品質；不適合精確維修步驟或頁碼佐證；成本較高，現有來源映射不能可靠還原原始頁碼 |
| DRIFT | 需要廣泛脈絡再逐步追問局部細節的多跳問題 | 多輪生成的 follow-up 可能偏離原問題；耗時與模型成本高；不代表每輪都找到正確證據，仍需檢查來源與覆蓋度 |
| Basic | 單一值、術語、警告或可能逐字出現在一段文字的精確查找 | 依賴向量相似度及 top-k；同義詞、型號格式、表格切分或跨段關係可能造成漏召回；不擅長全語料歸納 |
| 目前 Auto | 問題文字可明確對應某一策略時 | 只看問題即選一種方法；無檢索回饋、無證據充分度檢查、無策略重試或融合；fallback 固定 Local；模型給出的理由不構成正確性的驗證 |

答案正確率低不一定是策略選錯。應同時檢查 PDF 前處理／Vision、Text Unit 切分、索引抽取、來源 Metadata、召回證據、答案生成與評審標準，並把錯誤歸因到可觀測的階段。

Microsoft GraphRAG 將 Local 定位為特定實體推理、Global 定位為全語料總覽、DRIFT 結合 community 資訊與逐步 local 探索、Basic 作為標準向量檢索。新 Agent 應編排這些能力，而不是假設它們能互相取代。參考：[GraphRAG Query Engine](https://microsoft.github.io/graphrag/query/overview/)、[Local Search](https://microsoft.github.io/graphrag/query/local_search/)、[Global Search](https://microsoft.github.io/graphrag/query/global_search/)、[DRIFT Search](https://microsoft.github.io/graphrag/query/drift_search/)。

## 3. 目標設計：受限 Agentic Search

### 3.1 端到端流程

```text
問題與可選對話脈絡
  ↓
問題分析：抽取對象、條件、時間／型號及需要回答的子問題
  ↓
建立有上限的搜尋計畫
  ↓
呼叫 GraphRAG 白名單策略，取得 answer、query context、Evidence
  ↓
檢查子問題覆蓋、來源品質、重複及衝突
  ├─ 證據足夠 → 以證據為根據生成答案並附來源
  ├─ 有明確缺口 → 執行一個受限的補充搜尋步驟
  └─ 達上限仍不足 → 說明缺少的證據，不猜測
```

流程必須把「規劃」、「搜尋」、「證據檢查」和「最終作答」分開記錄。Agent 可以提議下一個允許的搜尋操作，但只能由程式驗證操作名稱與參數，再執行白名單中的 GraphRAG 查詢。

### 3.2 MVP 搜尋工具

第一版只提供下列受限工具：

1. `search_local(question)`：使用 GraphRAG Local，回傳回答、query context 和可解析的 Evidence。
2. `search_basic(question)`：以向量片段補足術語、警告、型號或單一數值查找。
3. `search_global(question)`：僅在問題確實要求跨文件歸納時使用；回傳 community report 層級來源並標示不可映射頁碼。
4. `search_drift(question)`：僅在需要多跳探索且預算允許時使用；第一版可先限制為一次 DRIFT 呼叫，不再任由 Agent 外層遞迴。

是否提供平行搜尋要由基準實驗決定。MVP 優先採「一次初始搜尋＋最多一次補搜」，避免所有問題都跑多種昂貴策略。

### 3.3 計畫與決策資料

Agent 的內部計畫應使用可驗證的結構化資料，例如：

```json
{
  "subquestions": ["問題一", "問題二"],
  "steps": [
    {"method": "local", "query": "受限的查詢文字", "purpose": "取得特定系統的原因與檢查依據"}
  ],
  "stop_after_steps": 2
}
```

實際實作須驗證 JSON schema、方法白名單、字數及步數上限。不可把 prompt 的自由文字直接當作命令執行。面向使用者的計畫說明、搜尋紀錄與最終回答使用繁體中文；送交 LLM 的所有指令 prompt 使用英文，使用者原始問題可保留原文。

### 3.4 證據充分度與衝突處理

- 對每個子問題記錄一筆或多筆 Evidence，至少保留 Evidence ID、文件、頁碼（若有）、Text Unit／context ID、原文及其來自哪個搜尋步驟。
- 檢查答案所需子問題是否都有可引用的原始文字 Evidence；只有 Global Community Report 時，標示為摘要型佐證，不偽造精確 PDF 頁碼。
- 將「有搜尋結果」和「證據足以支持答案」分開。LLM 自評信心只能當輔助訊號，不能作為唯一停止依據。
- 若來源互相矛盾，保留相反 Evidence，要求答案指出條件或差異；不得任意只留一方。
- 補搜應由可辨識缺口驅動，例如缺少步驟、數值、型號適用條件或第二個子問題，而不是單純因模型覺得答案不夠好。
- 達到輪數或成本上限仍無證據時，答案應明確回報未找到或未能確認的部分。

## 4. 分階段工作與驗收

### Phase 0：建立錯誤分類與評測基準

**工作**

- 盤點現有固定策略及 Auto 實驗結果，抽樣標記正確、部分正確、錯誤與無法回答案例。
- 對錯誤逐題標記主要原因：路由錯誤、證據未召回、證據不支持回答、答案推論錯誤、索引／前處理遺漏、題目或標準答案歧義、評審不一致。
- 建立人工審核的維修手冊題目集，包含精確規格／警告、症狀診斷、多步程序、跨系統因果、跨文件歸納、表格與圖表題，以及索引中確實不存在答案的負例。
- 每題記錄標準答案、必要答案要點、可接受同義說法及 Gold Evidence（文件、頁碼；必要時可含摘錄）。
- 用同一模型、同一回答格式與相同題目跑 Local／Global／DRIFT／Basic／目前 Auto，保存原始答案及 Evidence。

標註欄位、錯誤歸因順序與比較控制條件見[策略錯誤分析範本](策略錯誤分析範本.md)。已取得 `test_projects/SAMSUNG_Galaxy_S25_Ultra` 本機測試副本，不納入 Git。其 30 題皆有參考答案與 Gold Evidence；32 個 Gold 文件／頁碼標註均能對應來源 Metadata。題型主要是單本手冊事實查找，缺無答案、衝突、跨文件案例，且為手機使用手冊，僅能作窄範圍檢索試測。既有 3 題 Auto 的 Evidence Hit Rate 2/3、Document Hit Rate 3/3、Evidence Precision 6.7%、平均延遲 21.072 秒，尚非人工雙人覆核的正式基線。固定策略試跑遇 HTTP 401：3 次 Local 失敗；2 次 Global 因 map 呼叫失敗而回傳 canned「不知道」，不列入有效結果。副本 API Key 無效，已停止後續請求；更新有效連線設定後再跑 Basic／DRIFT 與完整策略對照。

**驗收**：每個標註答案均經人工抽查；基線可重現；錯誤有分類結果，能區分「路由問題」與「檢索／索引／生成問題」。在此之前不以 Agentic Search 對外宣稱精度提升。

### Phase 1：統一策略結果與可觀測性

**工作**

- 定義內部 `SearchStepResult`／`SearchEvidence` 或等價資料結構，統一方法、查詢文字、回答、原始 context、Evidence、錯誤、耗時、模型呼叫及參數版本。
- 擴充查詢結果紀錄，保存 requested method、實際每步方法、計畫、每步 Evidence、補搜原因、停止原因及總成本估計；舊版 `queries.jsonl` 仍可讀取。
- 釐清 GraphRAG query context 的 Evidence 排名與 `EvidenceService` 排名語意；無可信原始分數時不可將顯示次序偽裝成相關性分數。
- Global report 和 Text Unit 證據保留不同來源類型及其可追溯限制。
- 加入可由測試替換的 search executor 與 planner，避免單元測試呼叫真實 API。

**建議程式落點**：`querying.py`、`graph_query_worker.py`、`evidence.py`；新增策略協調模組，例如 `agentic_search.py` 或 `retrieval/` 套件。保持 `app.py` 主要負責 UI 接線。

**驗收**：四種現有策略仍能經統一介面執行；結果紀錄包含可重現每步所需資訊；舊查詢紀錄可載入；Global 和原文 Evidence 不混淆；既有固定策略行為回歸測試通過。

目前 Agentic 單題查詢已以 `SearchStepResult`／`SearchEvidence` 記錄每步方法、查詢、計畫目的、答案、原始 context、Evidence 類型、錯誤碼／訊息與耗時；查詢紀錄另存模型、推理深度、回應格式、prompt 版本、GraphRAG 設定檔 SHA-256、模型呼叫數、步數與停止原因。Evidence 的 `rank` 是顯示順序，沒有 GraphRAG 明確分數時 `score` 保持空值。舊 `queries.jsonl` 缺少新欄位仍可讀取。GraphRAG／Chat adapter 尚未提供 token 用量，因此成本估計明確為 `null`；非 Agentic GraphRAG 內部模型呼叫數亦標示未知，不能視為零。

### Phase 2：Agentic Search 離線原型

**工作**

- 實作英文 prompt 的問題分析／搜尋計畫輸出，程式端驗證 schema、方法、步數、查詢字數及允許參數。
- 實作白名單工具 adapter，只可呼叫既有 GraphRAG 搜尋，不允許自由工具呼叫或修改索引。
- 實作一次初始查詢與最多一次補搜；補搜需引用尚未覆蓋的子問題或缺失證據類型。
- 對每個搜尋結果抽取來源 Evidence，再執行證據整理與最終回答；最終答案需能將主要陳述連到 Evidence ID。
- 加入空結果、GraphRAG 失敗、LLM JSON 無效、Evidence 解析失敗、來源衝突及預算耗盡的安全處理。
- 以固定 Fake executor 測試計畫解析、工具限制、補搜條件、重複搜尋抑制及停止條件。

**初始資源上限建議**：每題最多 2 個 GraphRAG 搜尋步驟、最多 1 次規劃呼叫、1 次證據評估呼叫及 1 次最終整合呼叫；總時間上限先設 300 秒，不得平行展開無界子問題。精確數值應在基準集上量測後調整，並可在伺服器端設定上限。

**驗收**：Agent 不能呼叫白名單外方法；每題符合搜尋步數與呼叫上限；補搜有可檢查理由；所有引用 Evidence 都存在於實際 query context；來源不足或衝突時不編造頁碼或確定結論；單元測試不需真實 API。

目前原型已補上 Phase 2 離線安全案例：計畫與 Evidence 評估的 schema 驗證、重複補搜抑制、無可解析 Evidence 時停止生成並拒答、來源衝突指示、搜尋 executor 例外紀錄，以及時間預算耗盡時不啟動搜尋。真實模型與 GraphRAG context 品質仍未驗證。

### Phase 3：檢索實驗與品質／成本比較

**工作**

- 將 Agentic Search 接入檢索實驗組，結果保存每一步計畫、方法、Evidence 及停止原因。
- 與 Local、Global、DRIFT、Basic 及目前 Auto 使用同一題目集、相同回答模型及回答格式比較。
- 指標至少包含：答案正確率／部分正確率、必要答案要點覆蓋率、Evidence Hit Rate、Evidence Precision、Document Hit Rate、無根據陳述率、無答案題的正確拒答率、平均／P95 延遲、搜尋步數與模型呼叫數。
- 將檢索品質與回答品質分開分析；人工複核自動評分的代表性樣本，尤其是來源支持度與無根據陳述。
- 逐題保留失敗比較，確認新增 Agent 是否只增加成本而沒有提升目標題型表現。

**驗收**：報表可逐題對照方法、答案及來源；品質、延遲與成本指標定義清楚；測試集中的錯誤可回溯到計畫、召回、證據檢查或回答階段；只有在預先設定的品質門檻達成且成本可接受後，才建議將 Agentic Search 設為正式可選策略。

**執行進度**：已將 Agentic Search 加入「4 檢索實驗」獨立實驗組。每題保存搜尋步驟、方法、查詢、目的、回答、原始 context、Evidence、錯誤、耗時及停止原因；逐題表與 JSON 匯出可查看 trace。組別摘要提供平均／P95 延遲、搜尋步數、Agent 協調模型呼叫數、Gold Evidence 指標及成本未知狀態。另新增離線人工欄位：答案要點覆蓋率（0–100%）、無來源支持的主張數、無答案題拒答判定；摘要據已標註題目計算平均覆蓋率、含無根據主張回答率、平均主張數及拒答正確率。留白代表未複核，「不適用」不納入拒答正確率。此次變更不需要 API Key。完整策略比較、實際人工複核資料及品質門檻仍未完成；本次依使用者指示未執行測試。

### Phase 4：UI 整合與逐步發布

**工作**

- 在查詢方法中新增「Agentic Search（實驗）」選項；執行中顯示階段與進度，完成後可查看使用的方法、子問題、來源及補搜理由。
- 在檢索實驗中可把 Agentic Search 作為獨立組別，保存限制參數及版本。
- 將 Agentic Search 加入「3 自動問答測試」檢索模式；保留可調整的回答並行數，並清楚提示其額外模型呼叫與延遲。
- 保留目前 Auto 作為基準／回退選項；發布時可用設定關閉 Agentic Search。
- 更新使用指南、檢索策略文件、改善計畫及交接紀錄，記錄已驗證題型和限制。

**驗收**：管理頁能查看 Agent 步驟及來源；停用／錯誤回退路徑可用；舊固定策略及 Auto 不受破壞；服務使用新程式重新啟動且頁面可正常開啟；相關測試通過。

**執行進度**：單題問答與檢索實驗已提供 Agentic Search；本次依使用者指示直接加入「3 自動問答測試」的檢索模式，回答沿用 Agentic 每題最多兩次搜尋及既有並行數控制，並可用既有 Gold Evidence 指標評估已保存來源。自動問答與 Evidence 評測定向測試通過（16 項及 2 個子測試）；隔離啟動管理頁回應 HTTP 200，Gradio 設定確認選單列出 Agentic Search。此次不驗證任何資料集，也不據此宣稱品質提升。品質／成本比較與正式策略發布門檻仍待 Phase 0／3 評估。

## 5. 評測設計與發布門檻

### 5.1 題目分層

| 題型 | 例子／需求 | 預期觀察重點 |
| --- | --- | --- |
| 精確查找 | 指定型號、扭力、容量、警告原文 | Basic／Local 召回與數值正確性 |
| 特定實體維修 | 某零件位置、檢查程序、拆裝注意事項 | Local Evidence 是否涵蓋關鍵步驟 |
| 診斷多步題 | 症狀、可能原因、區分方式 | 子問題覆蓋、因果證據、補搜必要性 |
| 跨系統／跨文件 | 比較數個系統或多份手冊 | Global／DRIFT 的整合能力與引用限制 |
| 表格／圖表 | 表格規格、圖示解讀、流程圖條件 | Vision 解析與 Text Unit 可檢索性 |
| 無答案／歧義 | 文件沒有該規格或條件不足 | 是否正確拒答、是否避免臆測 |
| 衝突資料 | 不同型號／年份規格不同 | 是否保留條件並正確指出差異 |

### 5.2 門檻原則

- 先訂主要指標及可接受成本上限，再跑最終比較，避免事後挑選有利指標。
- Agentic Search 的整體正確率不得以少數題型進步掩蓋其他題型明顯退步；逐類回報結果。
- 至少確認答案支持度與無根據陳述率沒有惡化；精確維修題需人工檢視 Gold Evidence 對應。
- 若 Agentic 僅提升某類題型，應說明適用範圍，考慮按需路由，而非取代所有策略。
- 評測集與調整 prompt 的開發集分開；發布前保留未用於調參的 holdout 題目。

## 6. 資料與結果格式要求

每次 Agentic 查詢至少保存：

- 策略 ID、實作版本、planner／answer model、推理深度、prompt 版本、開始與完成時間。
- 原始問題、結構化子問題、計畫及每步使用的方法與查詢文字。
- 每步 GraphRAG 回答、原始 context 或可重建參照、解析出的 Evidence 與來源類型。
- 補搜的缺口理由、停止原因、錯誤與是否達資源上限。
- 最終答案、答案中的 Evidence 引用、耗時及模型／搜尋步數統計。

新欄位需提供預設值或遷移讀取，確保歷史 `queries.jsonl`、實驗匯出及 UI 歷史紀錄仍可讀。不可保存 API Key。原始查詢與文件片段依既有專案資料保護方式保存。

## 7. 主要風險與控制

| 風險 | 控制方式 |
| --- | --- |
| Agent 多呼叫模型但正確率未提升 | Phase 0 建立基準；限制搜尋輪數；發布前比較品質、延遲與呼叫數 |
| Planner 將問題拆錯或擴大題意 | 保留原問題；子問題須可追溯回原問題；最多一次補搜；加入無答案與歧義測試 |
| Evidence 排名被誤當相關性分數 | 只使用 GraphRAG 明確回傳的分數；無分數即標示未提供，不以列表次序冒充分數 |
| Community Report 被當成原文引用 | Evidence 類型分離；Global 報告不偽造文件頁碼；精確維修結論優先要求原文支持 |
| LLM 自評「證據足夠」但實際不支持 | 自評只作輔助；以 Evidence 對應、子問題覆蓋及人工 Gold Evidence 評測共同判斷 |
| 多策略或平行搜尋增加成本與負載 | 限制每題搜尋步數、批次併發及模型呼叫；統計 P95 延遲與單題成本 |
| 查詢內容被當成工具指令 | 所有搜尋工具採程式端白名單；模型只輸出 schema 化計畫；不接受任意程式或命令 |
| Vision／索引漏掉關鍵資訊被誤認為搜尋問題 | 將錯誤分類到前處理、索引、檢索、生成等階段；回報來源不存在時不盲目增加搜尋輪數 |
| 評測模型偏好冗長或特定措辭 | 使用人工抽樣覆核、必要答案要點與 Evidence 支持指標，不只看 LLM judge 分數 |

## 8. 完成定義

- 已用可追溯 Gold Evidence 的分層題目建立目前四種策略與 Auto 的基線。
- Agentic Search 只呼叫允許的 GraphRAG 方法，搜尋輪數及模型呼叫受到限制，整個過程可檢視及重現。
- Agentic 最終答案可對應到 Evidence；來源不足、來源衝突及無答案情況有明確處理。
- 同一實驗可以比較固定策略、目前 Auto 與 Agentic，並同時檢視正確性、來源支持、延遲及成本。
- 若未達預先訂定門檻，仍保留實驗功能與結果，但不將它標示為較準確的預設策略；失敗原因及下一步記錄於文件。
- 既有查詢、Evidence、歷史紀錄、檢索實驗及 portal 流程維持相容，相關測試通過。
